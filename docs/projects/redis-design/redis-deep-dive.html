🔴 Redis Deep Dive

A System Design Utility for Distributed Systems Architecture

1. The Redis Philosophy

Before touching data structures or commands, understand why Redis was built the way it was.

Core Insight: Redis is a Data Structure Server, Not Just Key-Value

Most people think "Redis = fast cache". That's like saying "PostgreSQL = table storage". Redis provides in-memory data structures with atomic operations — the speed is a consequence, not the purpose.

The Three Pillars

🧠 "Hot Path Data"

Redis lives on the "hot path" — data accessed frequently needing sub-ms response. It's your source of speed, not truth.

🧠 "Ephemeral + Renewable"

Treat Redis data as ephemeral. If Redis dies, can you rebuild from your durable store? If yes, you're using Redis correctly.

🧠 "Shared Scratch Space"

Redis is like a shared whiteboard between services — fast to read/write, everyone sees it, but you wouldn't store records there.

2. Core Architecture — The Single-Threaded Event Loop

This is the most important concept. Redis's single-threaded nature is not a limitation — it's the source of its power.

Why Single-Threaded Works: Redis operations are so fast (microseconds) that the CPU processes thousands of commands between network I/O events. The bottleneck is almost always network latency, not CPU time.

3. Data Structures — First-Class Citizens

Each data structure maps to specific use cases. Think of them as "primitives for distributed systems."

Strings — The Universal Primitive

Despite the name, Strings store any binary data up to 512MB. They're the building block for counters, caches, and simple key-value storage.

CommandDescriptionTime Complexity
SET key value [EX secs]Set with optional expirationO(1)
GET keyRetrieve valueO(1)
INCR key / DECR keyAtomic increment/decrementO(1)
SETNX key valueSet if Not eXists (for locks)O(1)
MGET key1 key2 key3Batch get (one round trip)O(N)

Rate Limiting with Strings (Simple Counter)

# Simple rate limit check with INCR
SET ratelimit:user:123 0 EX 60   # Create with 60s TTL
INCR ratelimit:user:123           # Returns current count
# If count > limit, reject request

Lists — Queues and Stacks

Doubly-linked lists. Perfect for message queues, activity feeds, and bounded collections.

Key Pattern: BRPOP / BLPOP are blocking operations — workers wait for new items without polling. Perfect for job queues.

Sets — Unique Collections

Unordered collections of unique strings. Use for tags, tracking unique visitors, set operations.

CommandDescriptionTime
SADD key memberAdd memberO(1)
SISMEMBER key memberCheck membershipO(1)
SINTER key1 key2IntersectionO(N*M)
SUNION key1 key2UnionO(N)
SDIFF key1 key2DifferenceO(N)

Use Case: Track online users per room, find mutual friends, tag systems.

Sorted Sets (ZSETs) — The Powerhouse

Sets with a score for each member. Automatically sorted. This is the key to rate limiting, leaderboards, and priority queues.

🔑 Rate Limiting with Sorted Sets

Score = Unix timestamp (ms) | Member = Request ID

ZADD ratelimit:user:123 1703849283000 "req-uuid-abc"
ZREMRANGEBYSCORE ratelimit:user:123 0 (now - window)
ZCARD ratelimit:user:123  → count in window

Hashes — Field-Value Maps

Think of them as "objects" or "records". Perfect for storing structured data like user profiles, sessions, or configuration.

HSET user:1001 name "Alice" email "alice@ex.com" plan "premium"
HGET user:1001 email           → "alice@ex.com"
HMGET user:1001 name plan      → ["Alice", "premium"]
HINCRBY user:1001 api_calls 1  → atomic counter within hash
HGETALL Pitfall: Avoid on hashes with many fields in hot paths — it returns all fields. Use HMGET for specific fields.

Streams — Append-Only Log (Your Pipeline Pattern!)

This is exactly what you described: Go pushing financial data, Python consuming it. Streams are Redis's answer to Kafka-style event streaming.

4. Clustering & Distribution

When a single Redis instance isn't enough: Replication (read scaling + failover) and Cluster (horizontal data sharding).

🔑 Hash Tags for Multi-Key Ops

Keys like {user:123}:profile and {user:123}:sessions land on the same shard. Essential for MULTI/EXEC across keys.

🔄 MOVED vs ASK Redirects

Clients get redirects when hitting wrong shard. Smart clients cache slot→node mapping.

⚠️ Cross-Slot Operations Fail

MGET/MSET across different slots = error. Use hash tags or client-side batching per slot.

5. Lua Scripting — Atomic Multi-Operations

This is the key to the rate limiter. Lua scripts run atomically — the single thread executes the entire script without interruption.

Why Lua?

Problem: You need to GET a value, check it, then SET conditionally. Between GET and SET, another client could modify it (race condition).

Solution: Wrap both operations in a Lua script. Redis executes it atomically — no other commands run in between.

Rate Limiter Lua Script (Sliding Window)

-- Rate Limiter: Sliding Window Log with Lua
-- KEYS[1] = rate limit key (e.g., "ratelimit:user:123")
-- ARGV[1] = current timestamp (milliseconds)
-- ARGV[2] = window size (milliseconds)
-- ARGV[3] = max requests allowed
-- ARGV[4] = unique request ID

local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local request_id = ARGV[4]

-- Remove entries outside the window
redis.call("ZREMRANGEBYSCORE", key, 0, now - window)

-- Count current requests in window
local count = redis.call("ZCARD", key)

if count < limit then
    redis.call("ZADD", key, now, request_id)
    redis.call("EXPIRE", key, math.ceil(window / 1000) + 10)
    return {1, limit - count - 1-- allowed, remaining
else
    return {0, 0-- denied, remaining
end
CRITICAL: Long-running Lua scripts block ALL Redis operations! Keep scripts short. Default timeout: 5 seconds.

Calling from Go

var rateLimitScript = redis.NewScript(`
    local key = KEYS[1]
    local now = tonumber(ARGV[1])
    local window = tonumber(ARGV[2])
    local limit = tonumber(ARGV[3])
    local request_id = ARGV[4]
    
    redis.call("ZREMRANGEBYSCORE", key, 0, now - window)
    local count = redis.call("ZCARD", key)
    
    if count < limit then
        redis.call("ZADD", key, now, request_id)
        redis.call("EXPIRE", key, math.ceil(window/1000) + 10)
        return {1, limit - count - 1}
    end
    return {0, 0}
`)

func CheckRateLimit(ctx context.Context, rdb *redis.Client, userID string) (bool, int64) {
    result, _ := rateLimitScript.Run(ctx, rdb, 
        []string{"ratelimit:" + userID},
        time.Now().UnixMilli(), 60000, 100, uuid.New().String(),
    ).Int64Slice()
    return result[0] == 1, result[1]
}

6. Temporal Considerations

Different time scales matter at different layers of a Redis system.

Pipelining — Amortizing Network Latency

Without Pipelining

# 3 round trips
SET key1 val1 → wait → OK
SET key2 val2 → wait → OK
SET key3 val3 → wait → OK
# Total: ~6ms (3 × 2ms RTT)

With Pipelining

# 1 round trip, 3 commands
SET key1 val1
SET key2 val2
SET key3 val3
→ send all → wait once → [OK,OK,OK]
# Total: ~2ms

7. Use Cases — Patterns in Practice

1. Rate Limiting (Sliding Window)

Structure: Sorted Set per user | Score: timestamp | Why Redis: Atomic operations, TTL cleanup, sub-ms latency

2. Session Storage

Structure: Hash per session ID | Pattern: SET with EX for timeout | Why Redis: Fast reads, auto-expiration

3. Caching (Cache-Aside)

Pattern: Check Redis → miss → fetch DB → write Redis with TTL | Why Redis: 100x faster than DB

4. Distributed Lock (Redlock)

Structure: String with unique token | Pattern: SET key token NX PX timeout | Why Redis: Atomic SET NX, auto-expire

5. Real-time Leaderboard

Structure: Sorted Set | Ops: ZINCRBY, ZREVRANGE, ZRANK | Why Redis: O(log N) sorted updates

6. Event Streaming / Message Queue

Structure: Stream with consumer groups | Pattern: XADD / XREADGROUP / XACK | Why Redis: Persistent, distributed consumers

8. Your Financial Data Pipeline

Go ingesting Morningstar data → Redis Streams → Python → WebSocket → React

Key Implementation Points

// Go Producer - batch with pipelining
pipe := rdb.Pipeline()
for _, update := range batch {
    pipe.XAdd(ctx, &redis.XAddArgs{
        Stream: "market:prices",
        MaxLen: 100000, Approx: true,  // Cap stream size
        Values: map[string]any{"sym": update.Sym, "price": update.Price},
    })
}
pipe.Exec(ctx)  // One network round-trip for entire batch
# Python Consumer - blocking read
entries = r.xreadgroup(
    groupname="analytics", consumername="worker-1",
    streams={"market:prices": ">"},  # ">" = only new messages
    count=100, block=1000  # Block up to 1 second
)
for stream, messages in entries:
    for msg_id, data in messages:
        # Push to WebSocket
        await broadcast(data)
        # Acknowledge processing
        r.xack("market:prices", "analytics", msg_id)
